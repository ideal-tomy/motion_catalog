# AI PROMO STUDIO｜既存UI/UX全体監査 → 情報設計 → 改善実装 指示書

## 依頼の目的

現在開発中のローカル版 AI PROMO STUDIO の **全操作画面を実際に調査**し、操作性・視認性・理解しやすさを改善してください。

現在の編集画面は、左側の「プロジェクト／素材／動き／AI部分修正」、中央のライブプレビュー、右側の「選択中のコマ／フレーム／画像／テキストの設定」、下部タイムラインという基本構成ができています。この土台を維持してください。

特に問題なのは、新機能の追加で右側・左側の設定項目が **常に大量に開いた縦長ページ** になり、目的の操作までのスクロールが長くなっていることです。

**各設定を意味のあるグループに整理し、必要な項目だけを開いて編集できる操作環境**へ改善してください。見た目だけアコーディオンにするのではなく、ユーザーが何を編集したいかに合わせ、必要な操作に最短で到達できる情報設計を行ってください。

## 実施順序（必須）

### Phase 0｜既存の状態・機能・テストを保護する

1. リポジトリ／起動手順／技術構成／画面コンポーネント／状態管理／保存経路を確認する。
2. `git status` と変更中ファイルを確認し、現在進行中の修正作業に影響しないようにする。ユーザーの変更を勝手に破棄・上書き・revert・reset しない。
3. 現在の画面を実際に起動して操作し、基準となるスクリーンショットと確認結果を記録する。
4. 色変更・フレーム変更・モーション適用・素材アップロードなど、既存の不具合修正と重なる箇所は、まず実装状況を確認する。未解決の不具合をUI改修で隠さない。
5. 既存のプロジェクトデータ、シーンID・レイヤーID、モーションID、JSON形式、保存内容、Undo/Redoの意味を不用意に変更しない。

### Phase 1｜現状UI/UXの全量監査（実画面＋コード）

画面を見るだけで判断せず、**全ての主要な操作を一度行う**こと。次の項目を一覧化する。

- 画面の領域：ヘッダー、左パネル各タブ、中央プレビュー、右インスペクター、下部タイムライン、ダイアログ／ポップオーバー。
- 存在する設定：項目名、適用対象、現在の配置、出現条件、編集すると何が変わるか、データの保存先。
- 操作対象：プロジェクト／コマ（シーン）／フレーム（表示領域）／画像・動画／テキスト／図形／モーション／音声。
- 操作導線：目的の設定へたどり着く手順、クリック数、縦スクロール量、タブの移動回数、類似操作の重複。
- 問題点：設定の重複、わかりにくい用語、不要な常時表示、長い縦スクロール、選択状態がわからない、編集の反映が見つけにくい、スクロール位置が飛ぶ、保存状態が不明瞭など。
- 画面サイズ：少なくとも 1920×1080、1366×768、狭いデスクトップ幅。タッチ操作でも基本操作に到達できるか確認する。

監査結果を `docs/UIUX_AUDIT.md` に記載する。各問題は **発生箇所 → 現状操作 → なぜ困るか → 改善方針 → 優先度** で整理する。

### Phase 2｜操作性・視認性・直感性のUI/UX再設計

`docs/UIUX_REDESIGN.md` を作成し、実装前に以下を定義する。

**A. 既存の大枠は維持**
- ヘッダー：プロジェクト名、保存状態、Undo/Redoなどの常時必要な操作。
- 左：構成／素材／動き／AI部分修正など、ライブラリと制作フローの入口。
- 中央：再生・停止・選択ができるライブプレビューを主役として十分な面積を確保。
- 右：現在選択中の対象に応じて内容が変わる「コンテキスト別インスペクター」。
- 下：シーンの時間軸、必要なときにコマ内のレイヤー／アニメーション時間軸を展開。

**B. 設定を『操作目的』で分類する**
例：右インスペクターのコマ選択時
1. 選択対象の見出し・現在の状態（常時表示、コンパクト）。
2. 「よく使う操作」：秒数・画面構成・選択対象の主要パラメータなどを最短で操作。
3. 折りたたみセクション：レイヤー一覧、配置・サイズ、素材／フレーム／マスク、テキスト、動き・タイミング、配色・効果、音声、AI引き継ぎ、詳細設定。

ただし、上記は仮案。**実コードに存在する機能を棚卸しした結果から最終分類を決定**し、既存機能を埋もれさせないこと。

**C. 選択対象によって必要な項目だけ表示する**
- コマ選択：尺、レイアウト、シーン全体の演出、シーンの色。
- フレーム／グループ選択：位置、サイズ、形状、マスク、内部コンテンツとの関連、フレーム自体のモーション。
- 画像／動画選択：差し替え、トリミング・フィット、枠内移動・ズーム、表示区間。
- テキスト選択：本文、フォント、文字サイズ・行間・色、タイプライターなどのテキストモーション。
- アニメーション選択：開始位置、長さ、方向、緩急、対象、複数モーションとの重なり。
- 何も選択していない場合：プロジェクト全体の設定、または次にする操作がわかるガイド。

**D. アコーディオンのルール**
- 初期状態では長い設定をすべて開かない。主な操作だけ見える状態にする。
- 項目名だけでなく、閉じている状態でも値の要約を表示する。例：`動き・タイミング｜右から登場 / 0.8秒`、`配色｜紺 + ミント`。
- 展開したセクション内で、まず主要項目、その下に「詳細設定」を置く。単純な一括非表示にしない。
- セクションの開閉だけでは編集値が失われない。別のコマ・レイヤーへ移動して戻っても変更値が維持される。
- 展開や選択によって意図せずスクロール位置が大きく飛ばない。必要な項目へ適切に移動できる。
- 一度に大量のアニメーション見本を再生しない。必要な内容を遅延ロードし、開閉操作を軽くする。
- 開閉状態は編集データとは区別して管理し、作品のJSONに不要なUI状態を混ぜない。
- キーボード・タッチで開閉でき、開閉状態が視覚とアクセシビリティ上で伝わる。

**E. 迷わない画面の基本原則**
- ユーザーが今「何を選択中」「何を編集している」「保存済みか」を常に把握できる。
- 操作が「追加」「選択」「試着」「適用／確定」「取り消し」「保存」のどれに当たるかラベルで明確にする。
- フレーム、コマ、レイヤー、動画フレーム（fps）という言葉の意味を混同しない。
- 設定の重複や配置の不統一を直す。ただし既存機能を削除したり、別画面に隠しすぎたりしない。
- 見やすくするためにフォントを一律に小さくしたり、単純にスクロール領域を増やすだけの対処はしない。
- 中央プレビューとタイムラインは表示を安定させ、左右の設定のスクロールに巻き込まない。
- 設定が見つからない場合に備え、機能名・操作目的で探せる「設定を探す」導線の実装可能性も評価する（初回実装の必須条件ではない）。

**F. 実装前の設計成果物**
- 画面領域ごとの簡易ワイヤーフレーム。
- 現状 → 変更後の操作手順比較（例：テキストにタイプライターを適用）。
- 各設定の所属先を漏れなく示す「旧UI項目 → 新UI配置」対応表。
- 初期表示、選択変更、開閉、Undo/Redo、保存・再読み込み時の振る舞い。
- 優先度（必須／次段階）と影響ファイル一覧。

### Phase 3｜段階的な実装

1. まず共有アコーディオン／設定セクションコンポーネントを作り、開閉、要約表示、キーボード操作、状態保持を統一する。
2. 右インスペクターを「選択対象別」に再編成する。全設定を移す前に、コマとテキストの2パターンで動作検証する。
3. フレーム、画像、図形、モーション、音声などへ展開する。
4. 左側タブの素材・モーションなども同じ原則で整理。検索とプレビュー導線は維持する。
5. タイムライン、プレビュー、選択中レイヤーとの同期を検証する。
6. 問題がなければ残りの細部（用語、余白、操作ボタン、選択表示、設定要約、狭い幅での振る舞い）を統一する。
7. 画面ごとに、変更前後のスクリーンショットを保存する。

作業の都合で追加機能の実装が必要になっても、今回の主目的はUI/UX改善。大規模な描画エンジンの書き換えやDBの再設計を始めないこと。

### Phase 4｜実ブラウザでの受け入れ確認

少なくとも次の操作を再現して結果を記録する。

1. 最初の画面で、主な作業の入口が一目でわかる。設定がすべて開いた縦長表示ではない。
2. 任意のコマを選択すると、コマに関係する設定が見える。秒数変更→タイムライン反映→保存ができる。
3. フレームを選択すると、配置・サイズやフレーム関連の編集へ容易に到達できる。
4. 画像を選択すると、差し替え・配置・枠内表示の編集へ容易に到達できる。
5. テキストを選択すると、本文と書式、タイプライター演出の設定へ容易に到達できる。
6. モーションを選び、適用、調整、プレビュー、取り消しができる。
7. 設定を開閉しても値や選択対象が消えない。別のコマに移動して戻っても値が保たれる。
8. 保存→ページ再読み込み→再選択でも、作品データが欠けない。
9. Undo/Redo・AI部分修正・編集メモ／引き継ぎ・素材アップロードなど既存の主要機能が維持される。
10. 1366×768程度でも、中央プレビュー、選択状態、主要な編集操作にアクセスでき、操作不能な狭い欄・多重スクロールが発生しない。
11. 開閉やタブ切り替えだけで過大な再描画や全モーション同時再生が起きない。

各項目を **確認済み／不具合あり／対象外（理由）** で報告する。目視のみでなく、可能なら既存の自動テスト・Playwrightテストを追加／更新する。

## 完了時の納品物

- `docs/UIUX_AUDIT.md`：現状の網羅的な課題・操作調査
- `docs/UIUX_REDESIGN.md`：新しい情報設計・画面構成・全項目移行表
- 実装済みコード（既存の保存形式・IDを維持）
- `docs/UIUX_VERIFICATION.md`：画面サイズ別・操作別のテスト結果、未解決事項
- Before / After のスクリーンショット
- 変更ファイル一覧と、次に改善すべき点

## 絶対に守る条件

- **監査 → 設計 → 実装 → 実画面テスト** の順番を省略しない。
- 前工程の資料を作成してから次工程へ進む。資料だけで終わらず、実装と動作確認まで実行する。
- 設定値の保存・プレビュー反映・AIへの引き継ぎ・MP4出力へのデータ接続を壊さない。
- ユーザーが編集中の素材・テキスト・色・シーン・レイヤー・モーションを勝手に初期化しない。
- 既存UIの単純な全面作り直しはしない。これまで使えるようになった機能を維持した改善とする。
- 未確認の項目を「確認済み」と報告しない。

## 作業開始時の返答フォーマット

最初に、①現状の画面とコードで確認した構成、②調査予定の編集導線、③監査レポートの保存先、④既存の作業・不具合との衝突リスク、を簡潔に報告してから着手すること。
