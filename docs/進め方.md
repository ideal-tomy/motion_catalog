## 次は「希望する印象 → 使用可能な演出 → 構成」の対応を作る

理想.mdの「素材側のタグ付け」を最初に行うのが適切です。60件すべての移植やWebサービス化より、既にある部品を正しく選べる状態を優先します。

### 1. タグと選択条件を整える

参照原本は変更せず、制作側 `src/catalog/registry.json` に付加情報を持たせます。動画素材にも案件内の `assets.json` を追加する設計を推奨します。

| 対象 | 推奨する軸 |
|---|---|
| モーション・トランジション | `mood`（energetic/calm/healing/cinematic）、`energy`（1〜5）、`pace`（slow/medium/fast）、`role`（hook/focus/transition/result/cta）、`motionType`（zoom/spin/reveal等） |
| 実画面の素材 | 機能、操作前/操作/結果、主役の領域、文字量、利用可能な尺、9:16への切り出し可否、確認根拠、利用条件 |
| 可読性・制約 | 読むための保持時間、動きの強さ、光量、適する画角、使えない場面、実装状態 |

「癒し」は単に速度を落とすだけでなく、揺れ・発光・音・色も含めた推薦条件にします。「緩急」は個々の素材のタグに加え、シーン間の強弱を決める構成ルールです。

合格条件：同じ素材から「迫力」「落ち着き」「緩急」の3候補を作り、選択理由と除外理由が分かる。未実装の演出を選んだ場合は移植が必要と表示し、動く扱いにしない。1本の標準案は3〜6種類程度。今回の全トランジション違いの作品は比較用プリセットとして残す。

### 2. 依頼と構成を共通化する

`request.json` に source・locale・duration・aspectRatio・tone・audience・goal・brand・CTAを整理し、`composition.json` にシーン・素材・演出・音声キューを集約します。schemaを定義して書き出し前に不整合を検出します。

「操作の価値を伝える20秒」「迫力を見せる22秒」「落ち着いた説明」のプリセットを作り、同じ素材を別構成で再利用します。連絡先は依頼で確認できた値だけ使用します。

合格条件：既存トーナメントとDDの両方を共通の依頼形式で再生成できる。既存4作品を上書きしない。

### 3. 撮影をアダプター化する

対象別の操作手順は分け、撮影サイズ・待機・証跡・サンプル情報・エラー記録を共通化します。ファイルパスや既存Playwrightの絶対パスは設定へ移します。対象アプリは読み取り専用を維持します。

合格条件：「開始画面 → 操作 → 結果」と根拠が素材一覧から追える。認証不能・未実装の機能は未確認として残る。

### 4. 縦型と任意尺に対応する

横型を単純に縮小せず、実画面の注目領域と文字位置を9:16向けに再配置します。render/QAの固定値とCompositionの登録方法も合わせて変更します。

合格条件：同じ案件で16:9と9:16を出力し、スマホで主役と字幕が読める。指定尺とフレーム数が一致し、音声付き全編再生を通る。

### 5. 制作画面と移植を増やす

素材・絵コンテ・タグ・差分を確認する編集画面を追加します。残りのモーションは利用頻度順に移植し、単体と完成動画で検証します。URL共有・ホスティングは別工程です。
