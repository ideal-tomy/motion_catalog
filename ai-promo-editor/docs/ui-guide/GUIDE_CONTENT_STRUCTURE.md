# 操作ガイドの内容設計

## 目的と入口

既存のアプリ内「操作ガイド」リンクから `/guide/` を開き、やりたいこと・画面の場所・画面用語のどれからでも手順にたどり着けるようにする。ガイドを別アプリ化せず、編集画面の見出しをそのまま使って実画面と往復しやすくする。

## 画面の構成

1. **検索**：一般的な言い方、画面上の名称、カテゴリ、手順に使う語をまとめて検索。全角半角差を吸収する。
2. **よく使う操作**：プロジェクトを開く、文字編集、素材追加、モーション試着などの入口。
3. **カテゴリ**：文字・レイヤー／シーン・タイムライン／素材・フレーム／動き・アニメーション／色・音声／保存・プロジェクト／AI修正・引き継ぎ／プレビュー。
4. **検索結果と詳細**：場所、条件、変更対象、手順、保存・戻し方、対応状況、実装根拠、関連操作。
5. **画面マップ**：実画面キャプチャとクリックできる領域別の操作入口。
6. **用語と対応範囲**：取り違えやすい操作、現在できることと未接続の機能。

## 操作項目のデータ項目

各操作を一件ずつ、単一の `ops` カタログに記録する。現行実装ではこのカタログをHTML内に保持して外部データファイルを増やさず、ガイドを一か所で保守する。

| 項目 | 内容 |
|---|---|
| `id` | 安定した短い識別子 |
| `title` | 行動で始まる操作名 |
| `aliases` | ユーザーが検索に使う自然な言い換え |
| `category` | ナビゲーション用分類 |
| `summary` | できることと対象外を一文で説明 |
| `location` | 実際の画面でたどる経路 |
| `condition` | 操作を表示・有効にする前提 |
| `scope` | 操作で変わる対象と影響範囲 |
| `steps` | 再現可能な手順 |
| `save` | 保存、Undo、キャンセルなど戻し方 |
| `status` | 利用可／条件付き／未対応／未確認 |
| `sources` | 実装上の根拠ファイル |
| `verifiedAt` | ソースとブラウザーで確認した日付 |
| `related` | 関連する操作ID |

## 作成・更新のルール

- UIや挙動を説明するときは、ソースだけで判断せず、表示条件を実アプリで確かめる。
- 「まだないUI」を利用可能のように書かない。未対応を操作詳細・機能境界の両方に明記する。
- 紛らわしい用語には同義語を足し、異なる対象を別の操作項目として登録する。
- スクリーンショットに載るプロジェクト情報・画面名・対象バージョンを記録する。ユーザーの制作素材を説明用画像に流用しない。
- ガイドの変更後は、既存のアプリ入口、検索、カテゴリ、詳細表示、画面マップ、デスクトップとモバイル幅、コンソールエラーを確認する。
- ガイド閲覧テストの前後で対象プロジェクトAPIのデータを比較し、説明書の表示が編集中の素材・プロジェクトを変更していないことを確認する。
- UI名称の提案と実装済みのラベルを混同しない。この資料は提案、アプリ表示は現状のままと明記する。
